## 1. Summary

Build a Rust implementation of `fenceline` alongside the existing Python one, not instead of it, exactly on the `spaghetti`/`spaghetti-rs` model: Python stays the spec of record and the easiest place to prototype a new check; Rust ships a single static binary with no interpreter dependency, for dropping into someone else's CI or pre-commit hook.

fenceline is arguably a **better-shaped** port candidate than spaghetti was: it's a similar size (~2,850 lines vs. spaghetti's ~3,000 of implementation, but with no cross-file/whole-package analysis at all — every one of its 56 checks operates on a single file in isolation), and its only non-stdlib runtime dependency is one ten-line helper (`boti.core.is_secure_path`, a `Path.resolve()`/`is_relative_to()` sandbox check — trivial to reimplement natively, not something to wrap or FFI into). The real open questions are narrower and more concrete than spaghetti's were: two specific regex patterns use lookahead syntax Rust's `regex` crate doesn't support (§7.1), and the tool's actual differentiator — a hardcoded CVE table — is a data-maintenance problem no port changes (§7.3).

## 2. Why

- **Zero-dependency distribution**, same rationale as spaghetti-rs: running `fenceline` today requires a Python 3.13+ environment (`tomllib` is used directly, so 3.11+ at minimum) plus `boti` as a runtime dependency pulled in for one function. A static binary drops into any CI image or pre-commit hook with nothing else installed.
- **Speed at scale** — less central here than for spaghetti, since fenceline's checks are simpler (mostly single regex passes over lines, not multi-pass AST complexity scoring), but still real: 56 checks × every file, each running `ast.parse` for the 13 AST-based checks even when just doing a line scan would do, adds up on large external codebases the way it does for spaghetti's `--config`/`--package` use case.
- **A clean-shaped tool to port.** No cross-file analysis, no import graphs, no structural-similarity scoring — the single hardest part of the spaghetti port (§7.2/7.3 there: `ast.dump()`-equivalent structural hashing, a from-scratch Ratcliff/Obershelp reimplementation because the `similar` crate's ratio diverged from `difflib`'s) simply doesn't exist here. Every check has the shape `(path, lines, tree) -> list[Finding]` and touches only its own file.
- **Reuses proven infrastructure.** `spaghetti-rs` already answered "does `rustpython-parser` parse this workspace's real Python cleanly" (111/111 files, 0 failures) and already has `regex`, `toml`, `serde_json` as dependencies. This isn't a port starting from zero-crate-experience.

## 3. Non-goals

- **Not deprecating the Python version.** It remains canonical — same framing as spaghetti (§5 there).
- **Not trying to make the Rust build own the CVE table.** The `vuln_deps` list in `manifest_checks.py` (currently ~15 hardcoded CVE entries) is a curated dataset, not logic — see §7.3 for where it should live so both implementations read the same data instead of maintaining two copies.
- **Not chasing all 56 checks in one phase.** Same reasoning as spaghetti §3: ship the easy majority first, grow into the two lookahead-dependent checks (§7.1) once a resolution for those is chosen.

### 4.1 Checks are uniformly simple — no tier structure needed

Unlike spaghetti's "30 easy + 3 hard" split, fenceline has no rule that needs anything beyond a single-file, single-pass scan. The AST checks (`check_pickle`-adjacent ones needing real parsing, e.g. `check_eval_exec`, `check_torch_load`, `check_pandas_eval`) still just walk one file's tree looking for specific `ast.Call`/`ast.Attribute` shapes — same tree-walk shape spaghetti-rs's per-file checks already use. There's no equivalent of spaghetti's `import-cycle` (needs a package-wide graph) or `sync-async-duplication` (needs cross-function text similarity).

### 4.2 No concurrency simplification to win

spaghetti's port got `rayon::par_iter()` "for free" by dropping Python's `ProcessPoolExecutor`/`Agent` multiprocessing dance (spaghetti §4.3) — but fenceline's `cli.py` was already a plain sequential `for path in sorted(...)` loop with no multiprocessing to begin with. The Rust port can still add `rayon::par_iter()` over files (checks are pure functions with no shared mutable state), but this is a genuine new capability, not a simplification of something already there — worth flagging as real, not automatic, scope.

### 4.3 One piece of non-Python-specific logic to reimplement: `is_secure_path`

`boti.core.is_secure_path(target, allowed_dirs)` is `config.py`'s and `cli.py`'s only import from outside fenceline itself — a directory-traversal sandbox check (`Path(target).resolve().is_relative_to(Path(allowed).resolve())` for each allowed dir). Trivial in Rust (`std::path::Path::canonicalize` + a prefix check), and since it's ~10 lines with no Python-specific behavior, this is copy-the-logic-once territory, not a dependency to design around.

## 5. Keeping two implementations honest: reuse spaghetti's conformance-suite design, don't reinvent it — ✅ done 2026-07-21

spaghetti's proposal (§5 there) already worked out the right mechanism for this exact problem — a shared golden-fixture corpus (`{input.py, expected.json}` pairs), Python as spec of record, message text allowed to differ but `cwe_id`/`severity`/`line` must match exactly, new rules land as a fixture with no implementation before either language builds it. That design transfers directly; built here as `fenceline/fixtures/<check_fn_name>/case_*.py` + `case_*.expected.json` pairs, diffed on `cwe_id`/`severity`/`confidence`/`line` (confidence added to the comparison since it didn't exist in spaghetti's Issue model — see §7.7) by a conformance runner at `tests/test_fixtures.py`.

What was different for fenceline going in, and how it played out:

- **The existing Python test suite was much thinner relative to rule count than spaghetti's was.** spaghetti had 152 tests across 36 rules (existing tests were largely already "one small source snippet, assert on the resulting Issues" — cheap to extract into fixtures). fenceline had 23 tests across 56 checks — 9 checks with direct unit tests (`check_pickle`, `check_pandas_eval`, `check_numpy_load` from the original 52, `check_debug_mode`, plus the 4 checks added post-spike: `check_bind_all_interfaces`, `check_weak_hash` (extended), `check_weak_tls_version`, `check_legacy_pycrypto`, `check_huggingface_unsafe_download` — see §7.7), leaving **47 checks with no existing unit test to extract a fixture from at all**. Built from scratch as expected: 57 fixture cases across those 47 checks (most get one case; a handful — `check_hardcoded_secrets`, `check_yaml_deserialize`, `check_format_string`, `check_eval_exec`, `check_except_pass`, `check_pth_startup_hooks`, `check_model_file_load`, `check_assert_security` — got 2-3 to lock in a documented false-positive guard or a severity-varies-by-flag behavior). A guard test (`test_every_check_without_a_dedicated_unit_test_has_a_fixture`) fails CI if a future check lands with neither.
- **First-pass fixtures were right 55/56 times** (98%) against the real, unmodified check functions — the one miss was genuinely useful: `check_assert_security`'s `\b(is|==|!=|in)\b` can't match `==`/`!=` written the normal way real code uses (`x == "y"`, spaces and a trailing quote) — `\b` needs a word-character transition on both sides of the match, and `=` bordered by a space on one side and a quote on the other never has one; confirmed directly (`re.search(r'\b==\b', 'x == "y"')` returns `None`). Not something to "fix" while writing fixtures — it's current behavior, and Python is spec of record — so it's now captured as two fixture cases: `is`/`in` forms that do fire, and a spaced-`==` form that provably doesn't.
- **The CVE/version table is data, not logic** (§7.3) — extracted to `vuln_deps.json`, loaded at runtime via `importlib.resources`, registered as package data in `pyproject.toml`. `check_dependency_cve` now iterates `(dep, cve)` pairs read from that file instead of a hardcoded Python literal.

## 6. Proposed Rust architecture

Reuses spaghetti-rs's already-validated choices wherever the same problem recurs; only rows fenceline needs that spaghetti didn't are new.

| Concern | Python | Rust choice | Why |
|---|---|---|---|
| Python parsing → AST | `ast` (stdlib) | `rustpython-parser` + `rustpython-ast` (same version spaghetti-rs pins) | Proven twice now: spaghetti-rs's original 111/111-file sweep, plus a fresh spike (§7.6) covering fenceline's own source and three repos that sweep never touched (436/436 files, 0 failures) and confirming every AST shape fenceline's 12 checks need is exposed correctly. |
| CLI parsing | `argparse` | `clap` (derive) | Direct match to fenceline's small flag set (`--json`, `--quiet`/`-q`, `--package`, `--fail-on`). |
| Line-based regex checks | `re` (stdlib) | `regex` crate only | Both lookahead patterns rewrite cleanly (§7.1, spiked) — no `fancy-regex` needed, dependency list matches spaghetti-rs's exactly. The 3 text-based checks added post-spike (§7.7) were written lookahead-free from the start (e.g. relying on `\b` boundary semantics — "Crypto" vs "Cryptodome" — instead of `(?!...)`), so this constraint is now shaping new Python checks too, not just the port. |
| Manifest text scanning | `re` (stdlib) over `.toml`/`.txt` **as plain text** | `regex` crate, no TOML parser needed | Confirmed by reading `manifest_checks.py`: both `check_dependency_cve` and `check_unbounded_pins` regex over raw lines, never `tomllib.loads()` the manifest — so, unlike spaghetti's workspace-root walk, this needs no `toml` crate dependency at all. |
| JSON output | `json` (stdlib) | `serde_json` | Direct match; also the fixture-diffing wire format per §5. |
| Sandboxing (`is_secure_path`) | `boti.core` | Inline reimplementation (§4.3) | ~10 lines, no crate needed. |
| Concurrency | none (sequential loop) | `rayon::par_iter()` over files — optional, new capability not present in Python (§4.2) | Checks are pure `(path, lines, tree) -> Vec<Finding>` functions with no shared state, so this is low-risk to add, but isn't required for parity. |
| CVE/version data | Hardcoded `vuln_deps: list[tuple[str,str,str]]` in `manifest_checks.py` | Shared `vuln_deps.toml` (or `.json`) loaded by both languages | See §7.3 — moves a currently Python-only literal into data both implementations read, the same "move hardcoded constants into one shared source" move spaghetti's proposal recommended for its own thresholds (spaghetti §5). |

## 7. Parity risk register

Phase 0's two spikes (§7.1 regex, §7.6 parser/AST) are both done, below, along with the smaller items they touched in passing (§7.2). Ranked by how much each could have changed the plan, not by resolution order.

### 7.1 Two regex patterns use lookahead — **spiked 2026-07-21, resolved: rewrite, no `fancy-regex` needed**

Found by grepping both check files for `(?=`/`(?<=`/`\1`-style backreferences:

- `checks/manifest_checks.py:75` — `check_dependency_cve`'s dependency-name matcher: `rf'(?:^|["\'=,\s]){re.escape(dep_base)}(?=["\':,<>=!\s]|$)'`, using lookahead to assert a word boundary after the dependency name without consuming it.
- `checks/text_checks.py:929` — a weak-hash-adjacent-to-security-context check: `r"hashlib\.md5\b.*(?=.*\b(?:sign|hmac|sig|token|password|hash\b))"`, using lookahead to check "does a security-sounding word appear later on this line" without anchoring the match's end to it.

Rust's mainline `regex` crate deliberately excludes all lookaround (lookahead/lookbehind) to preserve its linear-time matching guarantee — a permanent design constraint, not a missing feature. Checked both call sites in `manifest_checks.py`/`text_checks.py` first: **neither ever calls `.group()` on anything past the lookahead, and neither uses `.finditer()` for multiple non-overlapping matches on the same line** — both are pure `.search()` truthiness checks. That means the lookahead's defining property (zero-width, non-consuming) is never actually exercised by the code that uses it, which makes a consuming rewrite safe rather than just convenient.

Rewrote both and verified empirically rather than by argument alone — a small Rust spike (`regex` crate) and the real Python patterns run side-by-side against 133 shared test cases (120 dependency-name/line combinations covering substring-not-word-boundary traps like `boti-dask` vs `dask` and `pandas2` vs `pandas`, plus quote/comma/whitespace delimiter variations; 13 MD5-context lines covering true positives (`sig`/`token`/`hmac`/`password` context), true negatives (unrelated `md5_of_something`, non-security `sha256`), and case-insensitivity):

| Pattern | Rewrite | Result |
|---|---|---|
| `dep_pattern` | `(?=["\':,<>=!\s]\|$)` → `(?:["\':,<>=!\s]\|$)` — mechanical swap from lookahead to a consuming non-capturing group | 120/120 match Python |
| MD5-context | `hashlib\.md5\b.*(?=.*\b(?:sign\|hmac\|sig\|token\|password\|hash\b))` → `hashlib\.md5\b.*\b(?:sign\|hmac\|sig\|token\|password\|hash\b)` — the outer `.*` before the lookahead was already redundant with the `.*` inside it, so dropping the lookahead parens entirely and letting the outer `.*` consume through to the security term is a legal simplification, not just a syntax substitution | 13/13 match Python |

**0 mismatches across all 133 cases.** Both patterns compile and run correctly in the plain `regex` crate.

**Decision: reject `fancy-regex`.** Neither pattern needs it — rewrite both as ordinary consuming regexes, keep the dependency list exactly what spaghetti-rs already has (`regex` crate only, no second regex engine). This removes what would have been fenceline-rs's only crate-selection divergence from spaghetti-rs's proven dependency set (§6's table can drop the `fancy-regex` caveat).

One consequence worth carrying into Phase 1 (§5): the Rust source no longer textually mirrors the Python regex for these two patterns (the lookahead is gone, not just relocated), so these two specifically need a fixture in the shared conformance corpus, rather than relying on "read the two patterns side by side and see they match" the way most of the other ~50 checks can be spot-checked.

### 7.2 Deprecated `ast` node aliases used in one helper — **spiked 2026-07-21, confirmed non-issue**

`ast_helpers.py:108`'s `_has_dynamic_arg` checks `isinstance(arg, (ast.Constant, ast.Str, ast.Num, ast.NameConstant))` — `ast.Str`/`ast.Num`/`ast.NameConstant` are deprecated-since-3.8 aliases that Python's `ast` module still resolves (via `__instancecheck__` trickery) to plain `ast.Constant` under the hood. Confirmed directly from `rustpython-ast` 0.4.0's source (`builtin.rs`): its `Constant` is a single enum (`None`, `Bool(bool)`, `Str(String)`, `Bytes(Vec<u8>)`, `Int(BigInt)`, `Tuple(...)`, `Float(f64)`, `Complex{..}`, `Ellipsis`) with no separate legacy variants — so the Rust equivalent is just `matches!(expr, Expr::Constant(_))`, one match arm covering everything the four Python aliases jointly cover. Simplification confirmed, not assumed.

A related, more consequential confirmation from the same read: `Constant::Bool(bool)` is its own variant, distinct from `Int(BigInt)` — so `weights_only=True`/`allow_pickle=True` (`check_torch_load`, `check_numpy_load`, `check_insecure_default`) map to a clean `matches!(c.value, Constant::Bool(true))` check, exactly matching Python's `kw.value.value is True` identity check (which relies on Python `bool` being a real, distinguishable type from `int` at the object level, not just "truthy"). Verified empirically as part of §7.6's fixture, not just by reading the enum definition — `check_torch_load`/`check_numpy_load`/`check_insecure_default`'s spike results all matched Python exactly.

### 7.3 The CVE table is a data-maintenance problem, not a porting problem — ✅ extracted 2026-07-21

`manifest_checks.py`'s `vuln_deps` (10 entries: package/version constraint/CVE description) and the `CWE_REFERENCE`/CVE list in `reporting.py`'s docstring-style banner are hand-maintained, point-in-time security data — e.g. `CVE-2026-42208`, `CVE-2026-41486`, dated entries that will need updating long after any port ships. Porting this table into Rust as a second hardcoded literal would mean **every future CVE addition needs updating twice, in two languages** — the exact "two implementations drift" failure mode spaghetti's proposal identifies (spaghetti §5), except here it'd affect *data* nobody is proposing to keep in sync via a conformance suite.

Extracted as part of Phase 1: `vuln_deps` now lives in `src/fenceline/vuln_deps.json` (a flat `[{"dep": "...", "cve": "..."}]` array — dropped the unused `version_str` field the original hardcoded list carried, which duplicated `dep_name` and was never actually read anywhere in the loop body), registered as package data in `pyproject.toml`, and loaded once via `importlib.resources.files("fenceline")` (cached with `@lru_cache`). `check_dependency_cve` now just iterates the loaded list. When the Rust port reaches this check, it reads the identical JSON file rather than re-typing the table — the `CWE_REFERENCE` banner in `reporting.py` is unaffected (that's user-facing prose, not matched data the port needs to reproduce exactly).

### 7.4 Self-scan exclusion list needs to travel with the port, not be rediscovered — ✅ ported 2026-07-21

`scanner.py`'s `_SELF_SCAN_EXCLUDE` (checks/__init__.py, checks/text_checks.py, checks/manifest_checks.py, ast_helpers.py, reporting.py) exists because fenceline's own pattern-table source files necessarily contain, as string literals, the exact patterns they detect (a documented, deliberate design choice — see the comment in `scanner.py`). Ported as `scanner.rs::SELF_SCAN_EXCLUDE` (a `&[&[&str]]` of path-suffix-part arrays, matched by trailing-parts comparison, mirroring `_is_self_scan_exclusion`'s own suffix-not-absolute-path semantics) — verified with the same regression test Python's own suite uses (`iter_py_excludes_fencelines_own_check_definition_files`, transliterated directly).

### 7.5 Encoding tolerance — ✅ ported 2026-07-21, and found a real bug in the Python source while doing it

Same requirement as spaghetti §7.5: `_read()`'s `path.read_text(encoding="utf-8")` (with an exception caught and treated as "unreadable, skip" per `scanner.py`) must have a non-panicking equivalent in Rust — a scan shouldn't die on one malformed file in a large external codebase.

Re-reading `scanner.py` closely to port it faithfully found this wasn't just a theoretical risk: `_ast_parse`'s own `read_text()` call had **no encoding guard at all** — only `except SyntaxError` — while `_read()`'s had a broad `except Exception`. Worse, `_ast_parse` is called from `cli.py`'s main loop *outside* the per-check `try`/`except` (`tree = _ast_parse(path) if path.suffix == ".py" else None`, before the `for check_name, check_fn in CHECKS:` loop that's the only guarded region). A single malformed-UTF-8 `.py` file anywhere in a scanned codebase would have raised an uncaught `UnicodeDecodeError` and killed the entire scan — not "degrade gracefully for that one file," but a hard crash. Fixed directly in the Python source (`except (SyntaxError, OSError, UnicodeDecodeError)`, commit on the `fenceline` repo) with a regression test, rather than silently porting the bug into Rust and calling it faithful — "Python is spec of record" means matching *intended* behaviour once a genuine oversight is found and fixed, not preserving an accident. `scanner.rs::ast_parse` implements the corrected version directly (`std::fs::read_to_string(path).ok()?` before attempting to parse, so any read failure — missing file, permissions, bad encoding — degrades to `None` the same way a syntax error does).

### 7.6 Parser/AST-shape coverage for the 12 AST checks — **spiked 2026-07-21, resolved: `rustpython-parser` covers everything needed**

Two separate questions, both closed by one spike:

**(a) Does the parser/AST crate expose every node shape fenceline's 12 `checks/ast_checks.py` functions touch?** Read every check (§4's inventory) and catalogued the shapes: `Call` (func as bare `Name` or `Attribute` chain, `args`, `keywords`), `ExceptHandler` (`type_`/`name`/`body`, including the bare-vs-`Exception`-vs-other distinction), `FunctionDef`/`AsyncFunctionDef` (`args.posonlyargs`/`args`/`kwonlyargs`/`defaults`/`kw_defaults` for `check_insecure_default`'s parameter-default scan), `Assign`/`AnnAssign` targets, `ClassDef` methods (for `__arrow_ext_deserialize__`), and `Constant` (for the `allow_pickle=True`/`weights_only=True` literal checks). All present in `rustpython-ast` 0.4.0, confirmed by reading `gen/generic.rs` directly rather than assuming parity with Python's `ast` module — e.g. `Arguments.args`/`posonlyargs`/`kwonlyargs` are `Vec<ArgWithDefault>`, each pairing its own `arg` with its own `Option<default>` directly, which is actually **simpler to port** than Python's design (`ast_helpers.py`'s `_allow_pickle_default_lines` has to zip `args.defaults` against the *tail* of `args.args` by hand, since Python's parallel-array design doesn't pair a default with its arg directly — the Rust port skips that alignment logic entirely).

**(b) Does a Visitor built the way spaghetti-rs's was actually reach every `Call` node, no matter how it's nested?** This is the load-bearing question, because every one of fenceline's 12 AST checks is fundamentally "walk every `Call` node in the file and pattern-match it" — if the walker misses a `Call` wherever it's nested, the check silently misses the finding. spaghetti-rs already discovered (its §7.6) that `rustpython-ast`'s generated `Visitor`'s default `generic_visit_*` for four "support struct" node kinds — `Arguments`, `Comprehension`, `Keyword`, `WithItem` — are no-op stubs that don't descend into their children at all. Since fenceline's checks have the same "any `Call`, anywhere" shape, this matters here too, not just for spaghetti's rules.

Built a small spike crate (`rustpython-ast`/`rustpython-parser` 0.4.0, same pin as spaghetti-rs) with a `Visitor` that overrides `visit_arguments`/`visit_comprehension`/`visit_keyword`/`visit_withitem` using spaghetti-rs's exact fixed logic (copied directly from its `ast_helpers.rs`, not re-derived), plus a synthetic fixture (`fixture.py`) exercising all 12 checks' shapes — including three `eval()` calls placed deliberately in the exact spots spaghetti-rs's bug hid in: a comprehension's `if` filter, a function parameter's default value, and a call's keyword-argument value. Ran the real, unmodified `fenceline.checks.ast_checks` functions against the same fixture as ground truth.

**Result: 11 of 12 checks match Python's findings exactly, line-for-line — including all three deliberately-buried `eval()` calls.** The one apparent mismatch (`check_decode_exec_chains`: Python finds 2 findings at line 148, the spike finds 1) isn't a parser gap — that check has two independent detection paths in the Python source, a `Call`-based one (which the spike implements and which matched) and a separate multi-line text/regex scan needing no AST at all (which the spike deliberately left out of scope, per its own code comment, since it's a parser-capability spike, not a full reimplementation).

Also re-ran a parser-coverage sweep (not the full spike, just `rustpython_parser::parse` with no further processing) across every `.py` file in **fenceline itself** plus `etl-core`, `etl-demo`, and `ibis-etl-fastapi` — three repos spaghetti-rs's original 111-file proof never touched, since spaghetti-rs only scanned `boti`/`boti-data`/`boti-dask`/`spaghetti`. **436 files, 0 parse failures.**

**Decision: no parser blocker.** `rustpython-parser`/`rustpython-ast` 0.4.0, with spaghetti-rs's four walk-fix overrides carried over verbatim, is sufficient for all 12 AST checks. Nothing here changes the crate choice already recorded in §6.

### 7.8 fenceline also gained four architectural features the same day — real scope for Phase 2+, not just Phase 1

Separately again from both the port and the Bandit-catalog review, fenceline moved toward a general-purpose, pip-install-anywhere tool: **confidence rating** (a `Finding.confidence` field independent of severity — HIGH for AST checks, MEDIUM default for text checks, LOW for three explicitly heuristic ones), **plugin architecture** (third-party checks discovered via a `fenceline.checks` Python entry-point group; built-ins stay a static list), **baseline files** (`--baseline`/`--write-baseline`, fingerprinted on `(cwe_id, file, code_snippet)` rather than line number), and **`# nosec`/`# nosec CWE-502` inline suppression** (Bandit-compatible syntax, CWE IDs instead of B-numbers).

Unlike §7.7's check-count growth, these aren't just "more of the same shape" — each has a distinct Rust-port implication, not yet designed here:

- **Confidence** is the cheapest to port: one more `String`/enum field on the `Finding` struct and one more comparison in the CLI's filter logic, mirroring `SEVERITY_ORDER`'s existing pattern. §5's fixture corpus already asserts on it.
- **Baseline** is pure data-shape work (JSON read/write, a fingerprint tuple, a set difference) — no parser/AST involvement, low risk.
- **`# nosec`** is a regex over source lines, same shape as every other text check — but it runs as a *post-processing* pass over another check's output rather than being a check itself, which the Rust architecture needs a place for (not just a 57th entry in a checks list).
- **Plugin architecture** is the one with a real open question: it depends on Python's `importlib.metadata.entry_points()`, which has no Rust equivalent — a Rust plugin story would need something else entirely (dynamic library loading, a subprocess protocol, or WASM), which is a substantially different design question than "port a check," and is **not scoped by anything in this proposal today**. Recommend treating Rust-side extensibility as an explicitly deferred, separately-designed question when Phase 2+ gets there, rather than assuming it falls out of the existing phases for free.

### 7.9 `is_secure_path`'s Rust reimplementation has one disclosed divergence — found and accepted during Phase 2

Porting `boti.core.is_secure_path` (§4.3) surfaced a real semantic gap between the two languages' path-resolution primitives, not just a syntax difference: Python's `Path.resolve()` normalises a path lexically and follows symlinks **without requiring the path to exist** — it works fine on a path nothing has created yet. Rust's `std::fs::canonicalize` (the closest equivalent, and what `config.rs::is_secure_path` uses) **errors if the target doesn't exist**. Rust's standard library has no direct equivalent of Python's tolerant `resolve()` — building one (a manual lexical-normalisation walk that degrades gracefully past the first nonexistent component) is possible but is real, separate scope, not something to build silently as a side effect of porting a 10-line function.

**Decision: accept the divergence for now, documented in `config.rs`'s own doc comment.** It doesn't bite `default_packages` (Phase 2's only caller), which only ever checks real, already-existing package directories. It would matter for Phase 4's `--package NAME=PATH`, where a user could plausibly point at a path that doesn't exist yet (a typo, or a path they intend to create) — Python would resolve it anyway and let a *later* existence check fail with a clearer error; the Rust port as it stands today would instead fail closed at the security check itself, rejecting the argument with a security-shaped error message even though the actual problem is simpler ("that path doesn't exist"). Both outcomes reject the bad input; only the error message differs. Revisit if Phase 4 wants byte-identical CLI error text, otherwise this is a fine place to differ.

### 7.10 A real-workspace conformance mismatch during Phase 3 validation turned out to be a false alarm, not a port bug — methodological lesson

Phase 3's strongest evidence is the side-by-side real-workspace comparison (§10): run the Python CLI and the Rust `main.rs` driver over the same four packages (`boti`/`boti-data`/`boti-dask`/`fenceline`) with `--json`, diff the two reports. The first attempt at this diff showed 5 findings differing, all on `boti-data/pyproject.toml`, all a line-number offset rather than a different check or CWE — the shape of mismatch that (superficially) looks exactly like a real off-by-one bug in a manifest-line-counting check.

Before touching any Rust code, isolated the two candidate checks (`check_unbounded_pins`, and the manifest-file-discovery helper `find_manifest_files`) and called each directly against the file in question — both produced output matching Python's line numbers exactly, in isolation. That ruled out a logic bug in either function, which was confusing given the end-to-end diff still showed a mismatch. The actual cause surfaced from a system-reminder mid-investigation: `boti-data/pyproject.toml` was being **actively edited by the user in a separate, concurrent session** while the two scans were being run — so the two CLI invocations (Python first, Rust several minutes later) were not actually scanning the same file content. Re-running both scans back-to-back, immediately after the file's edits had settled, produced an **exact match across all 35 findings**.

**Lesson for future conformance work (Rust or otherwise): a real-workspace diff assumes the workspace is frozen for the duration of both scans.** On a live development workspace — as opposed to the vendored fixture corpus (§5), which is inert by construction — that assumption can silently break, and the resulting mismatch is indistinguishable at first glance from a genuine porting bug. The fixture corpus remains the trustworthy day-to-day regression signal precisely because it can't suffer this failure mode; real-workspace comparisons are a valuable *additional* check but should be re-run once, back-to-back with no gap, before trusting a mismatch as real — or before trusting a match as conclusive, for that matter, since a lucky pair of runs could just as easily agree by accident if both happened to straddle an edit in a way that cancelled out. Worth a beat of suspicion before writing off a rerun as unnecessary paranoia.

### 7.11 fenceline became a generic, pip-install-anywhere tool during Phase 4 — package resolution redesigned in both languages, and a real Rust line-number bug found by the rework

Mid-Phase-4, a separate but closely related piece of scope landed: fenceline's package-resolution logic was hardcoded to this workspace's own `boti`/`boti-data`/`boti-dask`/`fenceline` layout (`config.py::DEFAULT_PACKAGES`, keyed off an ambient `[tool.uv.workspace]` marker) and depended on `boti.core.is_secure_path` at runtime — neither is appropriate for a scanner meant to be `pip install`ed into an arbitrary, unrelated project. Fixed on the Python side first (spec of record), mirroring `spaghetti`'s own prior fix for the identical problem:

- **`is_secure_path` inlined** into `fenceline/config.py` (same ~10-line logic as `boti.core.is_secure_path`) rather than imported — the `boti>=1.0.0` runtime dependency was dropped from `pyproject.toml` entirely. A generic security scanner shouldn't drag in this workspace's own unrelated tooling as a hard dependency.
- **`discover_cwd_packages(cwd)`** added to `cli.py`, ported near-verbatim from `spaghetti/cli.py`'s own function of the same name: every immediate, non-noise subdirectory of `cwd` containing at least one `.py` file becomes its own named package; loose `.py` files directly in `cwd` become one more package named after `cwd` itself, scanned non-recursively so its already-registered subdirectories aren't double-counted. `DEFAULT_CWD_EXCLUDES` (a path-substring denylist — `.venv`, `.git`, `__pycache__`, `node_modules`, `build`, `dist`, `*.egg-info`, various tool caches) is applied *during* the recursive walk, not just at top-level directory selection, so a noise directory nested under a real package subtree is still skipped.
- **A bare `fenceline` invocation now auto-discovers `cwd`** instead of erroring with "no packages to scan" when no ambient `[tool.uv.workspace]` marker is present — this is the actual generic-tool behaviour: `pip install fenceline && cd anywhere && fenceline` now works. `--package NAME=PATH` opts back into an explicit registry, replacing auto-discovery entirely rather than merging with it (a deliberate behaviour change from the old `dict(PACKAGES); packages.update(...)` merge — matches `spaghetti`'s own semantics, where giving `--package` starts from an empty registry, not from a hardcoded default).
- **`--packages NAME [NAME ...]`** added (mirrors `spaghetti`'s own flag of the same name): narrows the resolved registry down to a named subset without changing how it was resolved. Distinct from singular `--package NAME=PATH`, which *builds* the registry.
- `config.py`'s `WORKSPACE_ROOT`/`DEFAULT_PACKAGES`/`PACKAGES` were kept, unused by the new default path, purely for `_rel()`'s relative-path display and test/API continuity — same as `spaghetti` itself still retains its equivalent constants for the identical reason.

**Ported to `fenceline-rs` the same day**: `cli.rs` gained `discover_cwd_packages`/`DEFAULT_CWD_EXCLUDES`/`is_noise_dir` (direct translations) and a `--packages` clap argument; `scanner.rs::iter_py` gained `recursive`/`exclude` parameters. `config.rs::default_packages` was left as-is (unused by the new default path, same as Python's `DEFAULT_PACKAGES`, kept for its own tests).

**A real Rust-only bug surfaced by re-running the real-workspace exact-match validation after this change**: the first post-rework comparison (auto-discovery now pulls in far more of the workspace — `boti/tests/`, `etl-core`, `etl-demo`, `ibis-etl-fastapi`, `fenceline-rs`'s vendored fixtures, etc. — 338 findings instead of 35) showed 5 mismatched findings, all `check_insecure_default` (CWE-453), all a small, consistent line-number offset on the *same* file each time (ruling out §7.10's concurrent-edit red herring — `git status` showed these files clean and untouched for over a day). Root cause: `ast_checks.py::_allow_pickle_kw_line`/`_allow_pickle_default_lines` deliberately report the line of the specific `allow_pickle=True` keyword's *value* node (or parameter default's own node), not the enclosing `Call`/`FunctionDef`'s own line — correct behaviour for a multi-line call or signature, where the dangerous keyword can sit several lines below the call's opening paren. The Rust `Collector` only ever recorded one line per `Call`/`FunctionDef` (the node's own start position) and reused it for every keyword-derived finding, which happened to be right for `check_numpy_load` (Python's own version also reports the *call's* line there) but wrong for `check_insecure_default` specifically. Fixed by adding `CallRec::allow_pickle_kw_line: Option<usize>` and a third `Option<usize>` field to `FuncDefRec`'s per-parameter tuple, each computed from the specific value/default AST node's own position rather than borrowed from the parent node. Re-validated: exact match restored, all 338 findings.
